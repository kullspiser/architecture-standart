# ADR — MVP. Подача заявок на депозит

**Автор:** Кулик Егор  
**Дата:** 8 февраля 2026  

---

## Функциональные требования

1. Пользователь должен иметь возможность просматривать перечень депозитных продуктов с действующими ставками, включая персонализированные условия.  
2. Пользователь должен иметь возможность оформить заявку на депозит, указав базовые контактные данные (ФИО, номер телефона).  
3. Сотрудник кол-центра обрабатывает поступившие заявки и при необходимости предлагает индивидуальные условия.  
4. Авторизованный клиент интернет-банка может подать заявку на депозит с указанием счёта и суммы, подтверждая операцию с помощью СМС-кода.  
5. Клиенту должен быть доступен просмотр списка депозитов и актуальных ставок без оформления заявки.

## Верхнеуровневые Use Cases

| № | Действующие лица / системы | Use Case | Описание |
|:-:|----------------------------|----------|----------|
| 1 | Пользователь / Сайт / Интернет-банк | Получение списка депозитов | Пользователь открывает сайт или интернет-банк, система отображает список депозитов с актуальными ставками; для авторизованных клиентов применяется персонализация. |
| 2 | Новый клиент / Сайт / Кол-центр / Фронт-офис | Подача заявки на депозит (с идентификацией) | Пользователь выбирает депозит и заполняет форму. Заявка сохраняется в системе кол-центра в зашифрованном виде. Менеджер связывается с клиентом, уточняет условия и направляет его на идентификацию в отделение. После идентификации заявка передаётся в АБС для подтверждения. |
| 3 | Клиент / Интернет-банк / СМС-сервис / Фронт-офис | Подача заявки на депозит | Клиент авторизуется в интернет-банке, выбирает депозит и подаёт заявку. Операция подтверждается СМС-кодом, после чего заявка направляется в АБС для обработки. |
| 4 | Бэк-офис депозитов / Бэк-офис кредитов | Обработка заявки | Менеджер депозитного бэк-офиса обрабатывает заявку в АБС, при необходимости запрашивает данные у кредитного бэк-офиса для расчёта ставки, оформляет документы и завершает открытие депозита. |

## Нефункциональные требования

| № | Требование |
|:-:|------------|
| 1 | Передача и обработка клиентских данных должна осуществляться с использованием защищённых каналов (TLS/HTTPS). |
| 2 | Сервисы должны функционировать круглосуточно с уровнем доступности не ниже 99.9%. |
| 3 | Сайт и интернет-банк должны поддерживать одновременную работу большого числа пользователей без прямого обращения к АБС. |
| 4 | Должна быть обеспечена возможность горизонтального масштабирования сервисов и инфраструктуры. |
| 5 | Время отклика при загрузке справочников и отображении ставок должно быть минимальным (уровень миллисекунд). |
| 6 | Пользовательский интерфейс должен соответствовать корпоративным стандартам дизайна и быть удобным для клиентов. |
| 7 | Все API и бизнес-процессы должны быть задокументированы для последующего развития решения. |
| 8 | Новые компоненты должны быть совместимы с существующим технологическим стеком банка (MS SQL, Oracle). |
| 9 | Микросервисная архитектура применяется ограниченно — только в рамках процесса открытия депозитов. |
| 10 | Персональные ставки должны обрабатываться с разграничением доступа между депозитным и кредитным бэк-офисом. |
| 11 | Должна быть предусмотрена возможность переключения на резервный ЦОД. |
| 12 | Подтверждение операций должно выполняться через существующее ядро СМС без доработки внешних сервисов. |

## Решение

Архитектурное решение ориентировано на обеспечение онлайн-подачи заявок на депозиты с соблюдением требований безопасности и отказоустойчивости.  
Основной акцент сделан на снижении прямой нагрузки на АБС, использовании существующих банковских технологий и обеспечении быстрого отклика для клиентов.  
Для этого используются промежуточные сервисы и асинхронные процессы обработки заявок с последующей передачей данных в АБС.

---

## Альтернативы

Были проанализированы ключевые альтернативные подходы к реализации решения:

- Доработка существующего интернет-банка рассматривалась как вариант, однако была признана рискованной из-за необходимости масштабного рефакторинга кода и вероятности нарушения привычного пользовательского интерфейса для лояльной клиентской базы.
- Создание нового интернет-банка с прямыми запросами к АБС на каждом шаге пользовательского сценария также анализировалось, но данный подход несёт риски, связанные с возможными ограничениями пропускной способности АБС.
- Разработка решения на базе Python + Flask была отклонена ввиду увеличения сроков реализации, обусловленного необходимостью освоения нового технологического стека командой.

## Недостатки, ограничения и риски

**Недостатки и риски:**
- Расчёт персональных ставок вручную (через Excel) повышает риск ошибок.
- Ограничение прямого доступа к АБС может усложнять обработку заявок.

**Ограничения MVP:**
- Новый клиент обязан проходить очную идентификацию в отделении.
- Полная автоматизация всех процессов и интеграция с другими продуктами банка не реализуются в рамках MVP.

**Риски безопасности:**
- Необходимо обеспечить корректное шифрование всех чувствительных данных при межсистемном взаимодействии.

**Ограничения технологического стека:**
- Используются только технологии, по которым имеется внутренняя экспертиза.
- Микросервисный подход применяется исключительно для процесса открытия депозитов.
